# 故障案例说明

AxiomOps 使用可重复的本地故障实验环境来验证诊断和恢复链路。每个案例都包含明确的 Ground Truth、观测信号、证据路径和恢复验证方式。

## 案例一：库存服务不可用

| 项目 | 内容 |
| --- | --- |
| 场景 | Inventory 服务返回 503 |
| 影响 | Order 服务调用库存依赖失败，订单链路被阻断 |
| Ground Truth | 库存服务处于 unavailable 模式 |
| 核心证据 | 服务健康异常、订单链路 503、Trace 中库存下游调用失败、Change Event 中存在故障注入记录 |
| 期望 RCA | 根因指向库存依赖不可用，而不是订单服务自身逻辑错误 |
| 恢复验证 | 重置库存故障后，Inventory 健康检查与 Order 链路同时恢复 |

推荐把这个案例作为默认演示，因为它最直观，能够清楚展示服务健康、订单链路、Trace 和 Change 之间的因果关系。

## 案例二：库存响应延迟升高

| 项目 | 内容 |
| --- | --- |
| 场景 | Inventory 服务响应时间显著升高 |
| 影响 | Order 服务下游调用变慢，可能触发超时或 SLO 风险 |
| Ground Truth | 库存服务处于 latency 模式 |
| 核心证据 | Prometheus 延迟指标升高、订单链路耗时增加、Trace 中库存 span duration 增大 |
| 期望 RCA | 根因指向库存下游延迟，而不是订单入口流量异常 |
| 恢复验证 | 重置故障后，库存延迟和订单链路耗时回落 |

这个案例适合展示 Metrics Investigator 与 Logs-Trace Investigator 的分工：指标负责发现“慢”，Trace 负责定位“慢在哪里”。

## 案例三：库存错误率异常

| 项目 | 内容 |
| --- | --- |
| 场景 | Inventory 服务按比例返回错误 |
| 影响 | Order 链路出现间歇性失败 |
| Ground Truth | 库存服务处于 error_rate 模式 |
| 核心证据 | Prometheus 错误率升高、订单链路探测出现失败、故障状态显示错误率配置 |
| 期望 RCA | 根因指向库存服务错误率异常，而不是网络完全不可用 |
| 恢复验证 | 重置错误率后，订单链路连续探测恢复稳定 |

这个案例适合展示为什么不能只看单次健康检查：服务可能不是完全不可用，而是部分请求失败。

## Evidence 到结论的映射

| Evidence 类型 | 回答的问题 | 在 RCA 中的作用 |
| --- | --- | --- |
| Metric Snapshot | 指标是否异常 | 判断错误率、延迟或下游失败是否存在 |
| Service Health | 服务是否可访问 | 区分服务不可用和业务链路异常 |
| Fault State | 实验环境当前注入了什么故障 | 提供 Ground Truth 对照 |
| Order Flow Probe | 用户链路是否受影响 | 证明故障是否影响真实业务请求 |
| Trace Snapshot | 请求卡在哪个下游调用 | 定位跨服务调用关系 |
| Change Event | 故障前后发生过什么变化 | 防止忽略近期变更导致错误归因 |

## 案例选择建议

- 默认展示：库存服务不可用。
- 强调性能问题：库存响应延迟升高。
- 强调部分失败与概率性问题：库存错误率异常。

三个案例共同证明：AxiomOps 不是围绕单一固定故障写死流程，而是围绕一套统一 Evidence Contract 处理不同故障信号。
